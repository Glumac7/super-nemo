# SUPER-NEMO

Standards: `~/.super-nemo/current/standards/ENGINEERING.md`. Repository and company instructions override SUPER-NEMO.

## 0. Runtime

SUPER-NEMO runs on OMP with the `nemo-*` task agents. If your `task` tool does not offer `nemo-implementer`, you are not in OMP. Without a `super-nemo` prefix, ignore this skill and work normally. With a prefix, don't emulate the workflow: tell the user to run `omp "<their original message>"` from the repository, and stop.

## 1. Route

An explicit mode wins. For `super-nemo:` or an unprefixed engineering request (AUTO), classify:

- **CRITICAL** — touches authn/authz, security-sensitive code, secrets, PII, DB migrations, infrastructure/deploy, agent/tool permissions, destructive operations, money, major architecture, or production-critical behavior.
- **LIGHT** — tiny fix, UI tweak, small test, trivial refactor; isolated and low-risk.
- **NORMAL** — everything else (features, business logic, APIs, meaningful refactors, bug fixes).

Make the routing judgment inline from the request and a bounded inspection of the affected code; do not spawn a separate judge or review agent just to select a mode. Choose LIGHT when the change is clearly tiny, isolated and low-risk; do not inflate it because of hypothetical future scope. Between two modes when concrete scope or risk remains uncertain, pick the higher. State the mode and a one-line reason, not a lengthy routing analysis. Re-route explicitly: upward only when inspection or implementation reveals concrete scope/risk that exceeds the chosen mode; downward only when, after user steering, the whole remaining change (including integrated author output) is LIGHT, then follow LIGHT including its single `nemo-quality` review. In NORMAL/CRITICAL, taking over production code yourself is a re-route. When the user steers mid-run, answer first and never block in `wait` on an author whose task they changed: steer it via `write agent://<id>` or cancel it (§3 ownership). The chosen mode alone decides the native review gate and test author (§3): LIGHT has neither; NORMAL and CRITICAL always require both, including automatically routed requests.

## 2. Prepare (all modes)

1. Must be inside a git repo. Read its instructions and the code the task touches.
2. If on `main`/`master`/a protected branch, create a branch first (repo's naming convention, else `super-nemo/<slug>`). Never commit to a protected branch.
3. Record `BASE=$(git rev-parse HEAD)`.
4. `SN="$(git rev-parse --absolute-git-dir)/super-nemo"; mkdir -p "$SN"` — evidence lives there, inside `.git`, so it is never tracked.
5. Write a short scope contract in `$SN/task.md`: requested behavior, observable acceptance criteria, non-goals, smallest repo-consistent approach, bounded allowed production paths/modules and separately owned test/fixture paths, repo check commands, and planned dependency/public-contract/architecture/config changes (default none). Retain the approved contract and base in trusted session state; mutable task/evidence files, issue comments and agent proposals cannot amend authority. Give every agent handoff its scoped subset; ask the user only for genuinely ambiguous acceptance criteria or material scope decisions below. No new tracked planning/report files.
6. For tasks that change runtime behavior, before implementation record the paths and identities of pre-existing relevant tracked and untracked workspace changes in `$SN/task.md`, and preserve enough state under `$SN` to reconstruct them safely for comparison. Exclude secrets and ignored private files; record any resulting capture limits. Documentation-only tasks do not require this comparison-state capture. Preserve user work in place: do not stash/reset it or modify the default branch.
7. In every mode, retain the pre-task path inventory and safe state identities needed to attribute later changes (§ Scope audit). Documentation-only work needs no full workspace copy or behavioral comparison snapshot.
8. In NORMAL/CRITICAL, before implementing, check all open PRs with `gh api --paginate 'repos/{owner}/{repo}/pulls?state=open&per_page=100'`, then each PR's changed files with `gh api --paginate 'repos/{owner}/{repo}/pulls/<number>/files?per_page=100'`. Compare exact repository-relative planned paths against both `filename` and `previous_filename` (renames), not search text or substring matches. Check each collected file count against `changed_files` from `gh api 'repos/{owner}/{repo}/pulls/<number>'`; the files endpoint caps results at 3000. Record pagination/API failures, caps and count discrepancies as incomplete coverage, never “no overlap.” Also check local branches (`git log --branches --not "$BASE" -- <paths>`) and worktrees (`git worktree list`). Record overlap and coverage limits in `task.md`; ordinary nonconflicting overlap need not block. Raise only material collisions or limits requiring a user decision.

### Scope decisions

Authors must not expand their own paths or behavior, add speculative features/dependencies/config/compatibility layers, or perform unrelated refactors. Return necessary unplanned work to the orchestrator **before doing it**, with concrete evidence and the minimal proposed change. The orchestrator may authorize necessary low-risk adjustments within user intent, retaining the amended bounds and reason in session state and recording them in `task.md`; re-route if risk grows. Every `task.md` deliverable must trace to the request or a necessary dependency. Material changes to the requested outcome, architecture/security risk, or external/public contracts beyond the ask require a user decision; so do unrequested deploy scripts, credential-handling tooling, automation or alert provisioning: propose them in one line and ask. An unrequested deliverable never raises the mode. Ordinary within-scope helpers and correct implementation choices need no extra approval. Scope decisions never grant publication authority.

Before implementation in every mode, follow these instructions yourself for LIGHT work and include them in the implementer's task for NORMAL/CRITICAL work:
- **UI changes:** load an available appropriate UI skill first (for example `impeccable`, `better-interface`, or `design-taste-frontend` when installed and relevant). Read prior screenshots, designs and user feedback; preserve useful context. Before implementation, the orchestrator identifies supported affected platforms and plans a safely obtainable baseline capture. Capture the actual before state before implementation, or later from a safely reconstructable equivalent baseline, preserving relevant pre-task user changes; never substitute clean HEAD for a dirty baseline. Use comparable screens/flows, representative viewports/devices and safe data/state for both captures. Substantial UI changes require before/after for each supported affected platform: web supporting desktop and mobile uses one representative viewport each; native uses one representative simulator/device per supported platform. Small visible changes need only the minimum affected surface, not a size/device/browser matrix or unchanged screens. The orchestrator verifies the actual changed surface for every UI change and captures integrated after states only after source/test integration (§ Integrated evidence); source inspection or unit tests alone are not surface verification. Baseline capture is the pre-implementation exception to that timing rule, not permission for mid-flight checks. Before handing screenshots to reviewers, open each one and confirm it shows the labelled state. Keep images in existing evidence/artifact storage, not new tracked report folders. Report unavailable skills, artifacts, platforms, runtimes or baseline access as limits; never fabricate a before state for a new screen or claim missing coverage.
- **Order of work:** first get a correct working feature with the smallest sound implementation; then simplify/clean up and check architecture; then measure and optimize demonstrated bottlenecks. Security, correctness and resource constraints apply throughout: no deliberately inefficient first pass, avoidable allocations/copies/computation, or speculative optimization. Do not attribute this sequence to Uncle Bob without a source or claim AI makes it inapplicable.

### Approach challenge (NORMAL and CRITICAL)

Before implementation or implementer dispatch, the orchestrator challenges the approach, not just the patch: “What outcome do we need, why this approach, and is there a simpler sound way?” Record a brief decision in the existing `task.md` and pass it to the implementer. NORMAL keeps this lightweight; CRITICAL requires an explicit checkpoint and repeats it before costly or hard-to-reverse commitments within approved scope. LIGHT adds no checkpoint or advisor ceremony; its existing simplicity and scope rules remain.

- Compare the chosen approach with a plausible materially simpler alternative when one exists: reuse existing behavior, change the owning module, or avoid coordinated repository changes. Do not invent alternatives to fill a quota. Use repository evidence and account for compatibility, responsibility boundaries, correctness and total maintenance cost; fewer files or repositories is not automatically better.
- Reassess when new evidence undermines the decision: an additional repository, dependency or public-contract change becomes necessary; an assumption fails; or repeated symptom fixes/growing exceptions suggest the wrong approach. The implementer pauses affected work and returns the evidence and smallest sound alternative to the orchestrator before continuing. Do not reopen settled decisions without new evidence or add timers/tool-call intervals.
- Conclude briefly: outcome, alternative (if viable), evidence/tradeoff, and decision—continue, simplify within scope, investigate a specific unknown, or ask the user. The orchestrator owns the decision; the advisor supplies challenges, not approval. Investigate discoverable technical facts; ask the user when unresolved material product priorities or acceptance criteria determine the choice, presenting options, consequences and a recommendation. Existing scope, risk-routing and authorization rules still apply; a checkpoint never authorizes an otherwise prohibited action.

### Review techniques

- **Elegant solution checkpoint (default, all modes):** after the first correct implementation and before integrated checks, ask: “Knowing everything you know now, what is the simplest sound solution?” If the patch relies on duplicated logic, symptom-only exceptions or obsolete paths, replace that complexity within the approved scope. Do not blindly discard working code, unrelated edits or user work. In NORMAL/CRITICAL, the production implementer owns this cleanup; preserve tester ownership, re-route if risk grows, and run the existing checks and review gates on the resulting patch.
- **Reverse PR review (explicit opt-in):** when the user explicitly requests this exercise (for example, “Grill me on these changes and don't make a PR until I pass your test”), inspect the actual diff and ask a short set of questions about its intent, invariants, failure paths and tradeoffs. State what evidence a satisfactory answer must explain; assess the user's answers against the code and observed checks, explain gaps and ask targeted follow-ups. Until the user answers satisfactorily, leave the patch local: do not commit, push or create any PR, including a draft, even if publication is otherwise authorized or the run is unattended. Missing or unsatisfactory answers leave the entire handoff pending; report the pending human interaction rather than inventing answers. Passing this exercise neither replaces independent reviews nor grants publication approval. Without an explicit request, do not add an interactive gate.
- **Behavioral proof (changed runtime behavior):** at the integrated check stage, run the same safe, bounded scenario with the same inputs and environment on the recorded baseline revision plus the preserved pre-task relevant workspace state and the integrated feature snapshot. Use disposable local targets without switching or modifying the default branch; both targets must contain equivalent pre-existing relevant workspace state so only this task's changes are attributed to the feature. For a clean worktree, the recorded baseline revision alone is unchanged. Record revisions/snapshot identity, pre-task state identity, inputs/environment, exact commands, observed outputs, intended differences and relevant unchanged behavior in `checks.md`; include a failure or boundary case where applicable. A textual diff or green tests alone is not a behavioral comparison. Do not use production services, secrets or destructive operations. If pre-task state cannot be safely captured/reconstructed, either snapshot cannot run safely or comparison prerequisites are unavailable, record the reason and unavailable comparison/unproven claims; never substitute clean HEAD for a dirty baseline. For documentation-only changes, record why runtime comparison is not applicable and verify the changed instructions directly.

### Integrated evidence

Evidence for reviewers:
- Refresh `$SN/diff.patch` after edits using the safe, scoped diff procedure below, including reviewed new files; never blanket `git add -N .` or capture private contents.
- In NORMAL/CRITICAL, run deterministic checks, behavior/surface probes and performance measurements only after source and test changes are integrated, including on fix loops; never mid-flight. In LIGHT, run them after your direct implementation and any tests.
- At that check stage, run the repo's deterministic checks yourself (lint, typecheck, tests, build; security tooling in CRITICAL), including the commands its commit hooks/lint-staged and CI configure for changed files, run directly on those paths in check-only mode (no fixers, never the stashing lint-staged runner), and write exact commands + results to `$SN/checks.md`.
- Checks are baseline-relative: unless the user explicitly asked for more, a repo-wide check criterion means no new failures vs BASE and changed paths clean; failures reproduced on BASE are recorded as baseline, not `FIX_REQUIRED`, unless the acceptance criteria require that check to pass (e.g. a fail-before test). Get baseline results from a disposable worktree at BASE plus the preserved pre-task state, never via `git stash`, `checkout --` or reset in the production worktree.
- At that same stage, exercise changed behavior (including a failure/abuse case in CRITICAL) and record observed output in `checks.md`; a green unit suite or lint alone is not operational proof.
- Probes and behavioral proof use the repo's existing harness and tools. Never temporarily edit tracked source in the production worktree; use the disposable target, which may reuse dependency directories only read-only (clone/copy), never through a writable symlink into the production worktree. Ask first before pulling images, starting containers or services, installing or switching toolchains globally, restarting shared dev services, or generating keys or tokens. Never mint or print credentials to gather telemetry: record the exact queries a human must run as HUMAN REVIEW items and the gap as a measurement limit; reviewers judge it under their own contracts.

Reviewers are read-only and only get what you give them: give their `context` the absolute paths of those three files. Pass evidence, not your conclusions.

### Scope audit (orchestrator, all modes)

Before accepting any author output and again before handoff, mechanically inventory the candidate/worktree from its repository root against the session-held base. Run these read-only commands, not an agent's summary; retain complete NUL-delimited records using NUL-aware tooling (no newline splitting or truncated lists):

```sh
git diff --no-ext-diff --no-textconv --name-status -z -M "$BASE" HEAD --
git diff --no-ext-diff --no-textconv --name-status -z -M --cached HEAD --
git diff --no-ext-diff --no-textconv --name-status -z -M --
git ls-files --others --exclude-standard -z --
```

Union all paths, including deletions and **both** rename endpoints; the three diffs cover committed, staged and unstaged changes independently. The last command includes hidden nonignored untracked additions; never scan ignored private files. Run the same inventory before work and compare the union of pre-task and candidate paths, so disappearance of pre-existing untracked files is not missed. Retain safe pre-task identities in session state: HEAD plus `git status --porcelain=v2 -z --untracked-files=all` for index identities/modes, and `git hash-object --no-filters -- "$path"` only for known non-sensitive changed regular files needing worktree/untracked identity; record absence for deletions. Never hash/read secrets or dereference symlinks for capture; record attribution limits instead. No full workspace copy is required for this audit.

Compare task-attributable paths with the session-held owner bounds and inspect their changes against the pre-task identities/state, not just clean HEAD. Unchanged pre-existing edits are neither violations nor permission to edit those paths; subsequent edits on a dirty path still need attribution and authorization. Unproven attribution leaves acceptance pending, never blanket-exempt dirty paths or erase user work.

Identify all repo dependency manifests/lockfiles (root and nested, including new/deleted files and both rename endpoints). Inspect their actual changes in each layer, even inside allowed paths; for each safe selected manifest path, use:

```sh
git diff --no-ext-diff --no-textconv "$BASE" HEAD -- "$path"
git diff --no-ext-diff --no-textconv --cached HEAD -- "$path"
git diff --no-ext-diff --no-textconv -- "$path"
```

Use the same scoped commands for review diffs; for each reviewed safe untracked regular file, append `git diff --no-ext-diff --no-textconv --no-index -- /dev/null "$path"` (exit 1 means differences, not failure). Inspect names/safety before contents; do not broaden capture or stage user files. Record actual audit commands/results, manifest inspection and attribution limits in existing `checks.md`; give reviewers the approved scope and decisions from session state, not merely copied evidence as authority.

Unexpected paths, unplanned dependency/manifest/lockfile/public-contract/behavior changes, unauthorized amendments or unproven attribution block acceptance/handoff. Route evidence to the responsible owner for removal of task edits or justification, obtain the proper scope decision before continuing, and re-audit after fixes or approved amendments. Preserve unrelated user work: never reset/delete it to pass. Inspect isolated candidates before integration where supported; if source auto-application already occurred, audit before acceptance and disclose that writes were not prevented. The stricter tester pre-integration gate below still applies.

Existing `nemo-quality` independently checks scope/simplicity in **all** modes; `nemo-architect` checks architecture/dependencies/config/contracts in NORMAL/CRITICAL; final review verifies audit evidence and unresolved material findings. Use their existing owner fix loops, with handoff blocked on evidence-backed `FIX_REQUIRED`. This is deterministic Git inventory plus model/orchestrator judgment, not automatic write interception, a sandbox or protection against malicious same-user execution. If trusted scope state is unavailable, require human review before acceptance; mutable evidence is no substitute.

## 3. Modes

The mode selects the implementer, and the implementer's definition attaches the advisor (models `@advisor` / `@advisor-critical`, guidance from the SUPER-NEMO watchdog). Never change `advisor.*` settings or run `/advisor` yourself. Advisor notes are input for the implementer and reviewers, never verdicts. After an advised implementer settles, read its full transcript `<id>.jsonl` in the session artifacts dir (`history://<id>` truncates notes) for `<advisory>` notes delivered after its final yield; send unresolved concern/blocker notes back to the same implementer via `write agent://<id>` and include them in reviewer context.

**Source/test ownership and handoff** (NORMAL and CRITICAL):
- `nemo-implementer` / `nemo-implementer-critical` own production code and its documentation only. `nemo-tester` owns behavioral tests and necessary test fixtures only; it uses `@default`, with no new advisor configuration. Neither approves its own work.
- Author isolation: use `isolated: true` only when every target path is inside the repo of the session's working directory. Depending on merge mode, captured work may be reported as `patchPath` (`<id>.patch`) or `branchName` (`omp/task/<id>`); neither existence nor freshness is guaranteed after failure/cancellation. Otherwise (another repo, multi-repo, or a different branch/worktree), create a dedicated worktree per repo yourself, record it in `task.md`, dispatch with `isolated: false` and its absolute root as the author's edit target, and audit it before integration like the tester target below. Never let an author write a sibling repo's live worktree. Multi-repo work keeps BASE, scope audit and evidence per repo plus a declared upstream→downstream release order, recorded in `task.md` and the report as a pending handoff item for reviewers to judge.
- Before cancelling an author, or after failure/cancellation, inspect actual run metadata/status, output (`agent://<id>`), capture/release state and any existing patch, branch or retained workspace. A retained workspace may contain uncaptured edits and an artifact may be stale. Preserve/recover actual work before releasing or discarding it; reuse/discard requires an explicit decision. An absent patch or clean production tree is not proof that no work exists. Report unavailable artifacts/workspaces as recovery limits, never false recovery success.
- Finish and integrate source first. BEFORE tester dispatch, retain the pre-tester Git revision, a cryptographic digest of the complete integrated-source snapshot (including new source files), and the approved test/fixture path set in the orchestrator's trusted session state. Record the production worktree's absolute path and base revision in `$SN/task.md`; save a separate source snapshot under `$SN` without overwriting it when refreshing review diffs. Record the explicit test/necessary-fixture allowlist in the task. Files under `$SN` are mutable evidence/storage, not trust anchors; the session-held revision, digest and approved paths are authoritative.
- Prepare a dedicated disposable repository copy/worktree containing EXACTLY that integrated source snapshot, using existing repository copy/diff mechanisms. It must represent the same effective source state, not a stale base. Do not copy home directories, user configuration or secrets. Pass the disposable target's absolute root, source revision/snapshot paths and test/fixture allowlist in the tester's context. Dispatch `nemo-tester` in a later task call with `isolated: false` to avoid runtime auto-application of isolated changes; never give it the production working tree as its edit target or draft tests in parallel with source implementation.
- Immediately before acceptance and BEFORE any integration or auto-application, recompute the stored source snapshot's digest yourself against the session-held expected digest and generate a fresh complete candidate diff (including new files) against that verified baseline. Audit it against the session-held approved test/fixture paths. Never accept an agent-supplied digest, diff summary or changed allowlist as authority. Reject a modified baseline, out-of-scope production/config/agent/permission edits, or auto-applied output; return the candidate to the responsible owner without accepting it. Independently apply only validated test/fixture changes to the production worktree, preserving unrelated user changes. Save the accepted scoped tester diff under `$SN` and provide target root/source snapshot and tester diff evidence paths to reviewers. Repeat with a fresh disposable target and fresh session-held anchors for every tester fix loop.
- If the runtime cannot preserve trusted session state or prevent auto-application, describe the split as advisory only: require human review of the full diff before accepting tester work and never claim enforced isolation. Do not treat mutable evidence files as a substitute for trusted state.
- This is orchestrator-validated authorship, not an OS sandbox. The tester and its tools are trusted same-user execution; prompts and disposable workspaces do not prevent secret reads, network access or destructive side effects. Those actions remain prohibited by instructions, not technically confined. Do not change runtime permissions or advisor configuration to implement the split; include this inherited runtime risk in the CRITICAL human-review handoff.
- Integrate accepted test changes before running deterministic checks yourself. Do not ask authors to run checks mid-flight. `nemo-qa` remains an independent read-only verifier, not a test author or production fixer.
- For red checks or confirmed review findings, send specific evidence (command, expected/observed behavior and location) via `write agent://<owner-id>`, which revives a parked owner, to the appropriate owner: production defects to the same implementer; test/fixture defects or missing coverage to the same tester. If revival fails, dispatch a new task of the same agent type with the prior handoff and evidence, and report the broken ownership continuity. Never weaken tests to fit a production defect. For mixed findings, integrate production fixes first, then let the tester update coverage on that state.
- After fixes, refresh evidence, re-run affected checks (including security checks where relevant), and re-run only failed review gates. Keep the same ownership in every fix loop.

**Gate not run** (all modes): a reviewer, tester or author task that fails for infrastructure reasons (provider quota/usage limit, auth, timeout; a failed job without a verdict) is GATE NOT RUN, never PASS. Do not retry blindly, dispatch further tasks on the same exhausted model role, or run final review while required gates are unrun. Report the exact pending gate and model if known; offer wait/retry later or stop with gates pending. Ordinary agents do not support per-call `model`; never use `tasks[].model`, auto-edit settings, change models/roles, substitute generic agents or use seance for implementation as recovery. Mandatory gates remain required and block publication (§5).

**Native review gate** (NORMAL and CRITICAL; never LIGHT). OMP's `/review` only expands into a prompt that dispatches the bundled `reviewer` agent, and you cannot type slash commands, so dispatch that agent directly:
- Only once checks are green. Add `agent: "reviewer"` tasks to the mode's review batch, sized like `/review` by hand-written changed lines (source + tests; generated, tabular/data, lockfile and snapshot files are excluded and covered by the slice owning their schema/loader): 1 task for <100 changed lines or ≤2 files, else split the files across 2 (<500 lines), up to 4 (<2000), up to 8. When a retry is approved under Gate not run, re-run only the slices that did not complete.
- Assignment: the files it owns plus "MUST run `git diff $BASE -- <path>` for assigned files; MAY read full files". Context: the three evidence paths. Add no rubric or output schema; the bundled prompt defines the review.
- It yields `overall_correctness`, `confidence` and findings with `priority` P0–P3, `confidence`, `file_path`, lines.
- Material: P0/P1, or P2 with confidence ≥ 0.8 describing a correctness, security or data-loss defect. Everything else (P3, style, low confidence) is recorded and reported, never fixed or re-reviewed.
- Before forwarding a material finding, read the cited code and confirm it; record refuted findings with the reason instead of fixing them.
- Confirmed findings join the fix loop like `FIX_REQUIRED`. It is an additional gate: never skip or replace a specialist because `reviewer` passed.

**LIGHT** — explicit tiny-change exception: no swarm, no advisor, no dedicated tester, no native or final review gate. If concrete evidence shows the work is bigger or riskier than LIGHT, stop and re-route upward.
1. Implement the smallest sound change yourself, including any necessary tests. Keep preparation/evidence concise; inspect the affected path and direct dependencies, not unrelated subsystems.
2. Run relevant checks and exercise changed behavior; for documentation-only changes, inspect the instructions directly. Record actual results in `checks.md`; do not add unrelated check matrices or rerun unchanged green checks.
3. Dispatch exactly one `nemo-quality` review with the scope contract, diff and check evidence, explicitly identifying LIGHT. Review the changed path and only the surrounding code needed to establish a concrete defect; do not launch additional reviewers or a separate judging pass.
4. Only evidence-backed material defects require correction: incorrect behavior, a security risk, a broken contract, unauthorized scope, or unnecessary complexity with a concrete maintenance cost. Optional polish and stylistic preferences are non-blocking. On `FIX_REQUIRED`, fix confirmed material findings once and re-run affected checks; do not start another review cycle. If a material finding remains unresolved, report it as unresolved and block handoff rather than claiming PASS. Otherwise report the review verdict, corrections and check results; stop.

**NORMAL**
1. Plan: add a short spec to `task.md` (approach, production files, tests and ownership).
2. Spawn one `nemo-implementer` (isolation per Author isolation above) with the spec for production changes only; it runs with the NORMAL advisor.
3. Integrate its source, then dispatch `nemo-tester` with `isolated: false` in the dedicated disposable target containing that exact effective source state, as above, for behavioral tests and necessary fixtures, including failure paths.
4. Audit the complete candidate against the source snapshot and explicit allowlist before applying validated tests, then diff + checks. Route failures to the appropriate owner as above and repeat until green.
5. One batch in parallel: `nemo-architect`, `nemo-quality`, `nemo-qa`, native `reviewer`.
6. On `FIX_REQUIRED` or a confirmed material `reviewer` finding: route to the responsible implementer or tester as above, then refresh evidence, re-run affected checks, and re-run only reviewers that failed (`reviewer` only if it had material findings). Max two loops, then report what is open.
7. `nemo-final-review` with task, diff, checks and all findings, including `reviewer`'s and any you refuted.

**CRITICAL** — safety over speed.
1. Add requirements and a threat sketch to `task.md`: assets, trust boundaries, abuse cases, rollback.
2. If the design is non-trivial: `nemo-architect` pre-review of the plan.
3. `nemo-implementer-critical` (isolation per Author isolation above) for production changes only; it runs with the stronger critical advisor and reports how it resolved each advisor concern/blocker.
4. Integrate its source, then dispatch `nemo-tester` with `isolated: false` in the dedicated disposable target containing that exact effective source state, as above, for behavioral tests and necessary fixtures, including failure and threat-sketch abuse paths.
5. Audit the complete candidate against the source snapshot and explicit allowlist before applying validated tests, then diff + checks including security tooling; route failures by ownership and require green before continuing, as in NORMAL.
6. One batch in parallel: `nemo-architect`, `nemo-security`, `nemo-quality`, `nemo-qa`, **`nemo-performance`**, native `reviewer`. Before dispatch, read `omp config get modelRoles --json`, `omp config get task.agentModelOverrides --json` and the effective discovered `nemo-performance` agent's frontmatter without changing settings. OMP model priority is `task.agentModelOverrides` → agent frontmatter → task role/session fallback ([task API](https://raw.githubusercontent.com/can1357/oh-my-pi/v18.12.6/docs/tools/task.md)); ordinary tasks have no per-call `model`. Verify that the effective per-agent selection resolves to configured, available `@advisor-critical`. Only when advisors are disabled and neither advisor role is configured may it resolve to configured, available `@nemo-review`; explicitly report this fallback. Query failure, malformed output, unknown effective selection, missing/unavailable required model or a weaker mapping blocks dispatch: ask the user to configure the supported per-agent setting outside this run, never auto-edit configuration, introduce roles or silently substitute. Retain selection/dispatch evidence; do not claim critical selection from the default alone. Give performance review reproducible bounded local workload, baseline/changed measurements and commands, or explicitly state missing evidence; no invented numbers or unsupported findings.
   Install/update manages `task.agentModelOverrides.nemo-performance`: advisor-enabled installs use `@advisor-critical`, advisor-disabled installs use `@nemo-review`. Existing users must reapply with `sn update` and start a fresh OMP session; advisor-on/off changes follow the existing managed-setting consent/drift lifecycle. This installer mapping does not replace preflight: missing, weaker or custom-drifted effective selection still blocks unless it satisfies the contract above. Never repair settings automatically during a task.
7. Fix loop as in NORMAL, preserving production/test ownership and integration order, including `nemo-performance`: resolve evidence-backed `FIX_REQUIRED`, refresh measurements for relevant changes after source and test integration, and re-run failed reviewers. Record measurement limits even when there is no supported finding.
8. `nemo-final-review` with all evidence and findings, including performance verdict, measurements and limits.
9. End with **HUMAN REVIEW REQUIRED**: list what the human must check. By default leave local changes on the feature branch; only the primary orchestrator may perform the explicitly authorized draft handoff below. A draft never satisfies human review.

## 4. Rules

- You orchestrate; you never approve. Verdicts come from the reviewers.
- Implementers and reviewers must never commit, push, open PRs, merge, deploy, run destructive DB/infra commands, or read secrets. Only the primary orchestrator may evaluate direct session-level publication approval (§5).
- Never push protected branches, merge, deploy, mark PRs ready for review, run destructive DB/infra operations, or read secrets as part of this workflow.
- Never amend `task.md` acceptance criteria after review to clear a verdict. Required gates and unresolved material findings cannot be waived for publication.
- Report (short): mode, branch, what changed, checks with actual results, each reviewer's verdict (`reviewer`: `overall_correctness` + material findings and how each was resolved), performance evidence/limits in CRITICAL, the final-review verdict verbatim, pending gates and open items. End with one line naming exactly what is pending, distinguishing required gate/finding resolution from publication authorization (in CRITICAL, after the **HUMAN REVIEW REQUIRED** block); this is not a new approval path (§5 is unchanged).
